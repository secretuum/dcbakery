Трудозатраты: **S** (полчаса-час), **M** (полдня-день), **L** (несколько дней / рефакторинг). Уверенность: high / medium / low.

## Группа A. Быстрые победы (high/medium эффект, S-M усилий)

### A1. LCP-героя: плавающий тег — фото 135 КБ показано как иконка 40×40
- **Где:** `app/(main)/page.tsx:132`
- **Проблема:** `<img src="/products/pelmeni-s-govyadinoy.webp">` с классом `size-10` (40×40px), а исходник весит **135 616 байт** — полноразмерное фото товара. Отдаётся as-is, в первом экране, конкурирует за полосу с LCP.
- **Что сделать:** заменить на `next/image` с `width={40} height={40} sizes="40px"` (дериват — единицы КБ), либо подготовить отдельный ассет 80×80. Чистая SAFE-зона.
- **Эффект:** −130 КБ на первом экране. **Трудозатраты:** S. **Уверенность:** high.

### A2. Нет preconnect к аналитике и Supabase Storage (в layout вообще нет `<head>`)
- **Где:** `app/layout.tsx:113` (подтверждено: `<head>` отсутствует, сразу `<body>`)
- **Проблема:** DNS+TCP+TLS к googletagmanager.com / google-analytics.com / mc.yandex.ru открываются лениво в момент выполнения скрипта; к `*.supabase.co` (фото товаров) — в момент запроса первой удалённой картинки. Холодное рукопожатие задерживает и первый page_view, и LCP каталога, если LCP — фото из Supabase.
- **Что сделать:** добавить `<head>` в RootLayout с `<link rel="preconnect">` (+ `dns-prefetch` фолбэк) для GA/Метрики (условно по наличию `NEXT_PUBLIC_GA_ID`/`NEXT_PUBLIC_YANDEX_METRICA_ID`) и для origin из `NEXT_PUBLIC_SUPABASE_URL` (`crossOrigin="anonymous"`).
- **Эффект:** −100…300 мс на медленных мобильных до первой картинки/аналитики. **Трудозатраты:** S. **Уверенность:** high.
- *Дедуплицировано:* объединяет исходные находки про аналитику (preconnect) и Supabase-preconnect — правка одна и та же.
- *Смежное:* CSP (`next.config.ts:29`) не задаёт `script-src`/`connect-src`, поэтому preconnect добавится без конфликтов. Действий для скорости не требует.

### A3. Стоп-лист: два запроса к Supabase вместо одного
- **Где:** `app/(main)/admin/stop-list/page.tsx:22`
- **Проблема:** `Promise.all` делает `fetchProductStopEvents({activeOnly:true})` И `fetchProductStopEvents()` (весь список). Активные — подмножество полного (`ended_at is null`, `admin.ts:436-438`). Второй запрос полностью покрывает первый.
- **Что сделать:** один `fetchProductStopEvents()`, `activeEvents = events.filter(e => e.ended_at == null)` в памяти.
- **Эффект:** −1 сетевой round-trip на каждый рендер. **Трудозатраты:** S. **Уверенность:** high.

### A4. `fetchAppSettings` делает SELECT * — тянет крупный `home_layout` в кэш site_content
- **Где:** `src/lib/supabase/admin.ts:381` (подтверждено: `select=*&order=key.asc`)
- **Проблема:** `getSiteContent()` берёт только строку `key='site_content'`, но `SELECT *` тянет ВСЕ строки `app_settings`, включая крупный JSON `home_layout` (конструктор главной). На каждой ревалидации кэша (раз в 3600с + каждый `revalidateTag` после правки в админке) — лишний egress.
- **Что сделать:** ограничить запрос ключом: `select=key,value&key=eq.site_content`.
- **Эффект:** одна маленькая строка вместо всей таблицы в окне ревалидации. **Трудозатраты:** S. **Уверенность:** medium.

### A5. Category page: `fetchCategoryBySlug` резолвится дважды + каталог пересобирается
- **Где:** `app/(main)/catalog/[category]/page.tsx:54`; `src/lib/catalog.ts:383-384,293-295`
- **Проблема:** `fetchCategoryBySlug(category)` ждётся последовательно (стр.54) до `Promise.all` (стр.60). Внутри `Promise.all` `fetchProductsByCategory` СНОВА вызывает `fetchCategoryBySlug`. Плюс `getActiveCategories()`/`getSourceProducts()` пересобираются на каждый вызов `getCatalogProducts`. Overrides кэшированы (egress не растёт), но это лишний CPU на каждый запрос — страниц категорий немного, но краулеры обходят их часто.
- **Что сделать:** резолвить `currentCategory` один раз и передавать products из общего `getCatalogProducts`, отфильтрованного по `category_id`, вместо `fetchProductsByCategory(slug)`. Мемоизировать `getActiveCategories`/`getSourceProducts` на модуль (они статические).
- **Эффект:** меньше CPU/TTFB на категориях под краулерами. **Трудозатраты:** S. **Уверенность:** high.

### A6. LCP каталога: первые карточки товара не помечены `priority`
- **Где:** `src/components/catalog/ProductCard.tsx:79`
- **Проблема:** `ProductCard`/`HomePopularPosters` используют `next/image` через `FallbackImage` с корректными `fill`+`sizes` — это хорошо. Но ни одна карточка не помечена `priority`; на `/catalog` LCP — обычно первое фото над сгибом, грузится лениво/с обычным приоритетом. `FallbackImage` прокидывает `...props`, т.е. `priority` уже поддерживается технически — просто нигде не передаётся.
- **Что сделать:** передавать `priority` первым ~4-8 карточкам первого ряда (по индексу), остальные — как есть. Аналогично первому постеру `HomePopularPosters`, если он в первом экране.
- **Эффект:** заметно быстрее LCP каталога. **Трудозатраты:** S. **Уверенность:** medium.

### A7. У Geist (основной шрифт) не задан `display:swap`

## Группа B. Структурные работы с высоким эффектом (high эффект, M-L усилий)

### B1. Оба словаря kk.json (153 КБ) + en.json (119 КБ) статически бандлятся в клиент
- **Где:** `src/i18n/translate.ts:1-2` (подтверждено: `import kk from ...kk.json`, `import en from ...en.json`)
- **Проблема:** `translate.ts` статически импортирует оба словаря (~272 КБ сырого JSON). Модуль тянется клиентским `src/i18n/client.tsx` (`useT`/`useLocale`), используемым 29 клиентскими компонентами (Header, Footer, ProductCard, CartSheet, все `home/*`). Итог: **оба словаря целиком уезжают в общий клиентский чанк и грузятся на КАЖДОЙ странице у КАЖДОГО посетителя** — включая ru-локаль, которой словари не нужны (`translate.ts:19-20` для ru возвращает оригинал). Это не egress — чистый вес клиентского бандла и время парса на мобильных.
- **Что сделать (по возрастанию усилий):** (1) грузить нужный словарь по локали через динамический `import()` внутри провайдера (kk и en в отдельных чанках, ru — вообще без словаря); (2) отдавать активный словарь один раз с сервера в `LocaleProvider` как проп; (3) минимум — разнести kk и en в отдельные динамические чанки. Проверить бандл ANALYZE-сборкой (не на проде) до/после.
- **Эффект:** −один-два словаря целиком из каждого первого захода; для ru-посетителей — минус оба. **Трудозатраты:** M. **Уверенность:** high.

### B2. LCP-изображение героя — голый `<img>` без next/image, priority и fetchpriority
- **Где:** `src/components/home/SiteEditMode.tsx:648` (публичная ветка `EditableImage`); главное фото — `app/(main)/page.tsx:113`
- **Проблема:** все три фото сцены героя (`imgMain/imgA/imgB`, `page.tsx:113,120,127`) выводит `EditableImage`, который в публичном режиме возвращает обычный `<img src>` без width/height, без `fetchpriority`, не через `next/image`. Главное фото (`tort-medovik.webp`, до 520px+) — это LCP первого экрана; грузится с приоритетом «auto» (фактически low для картинок), после шрифтов/CSS. Нет `fetchpriority="high"`, нет preload, нет resize/AVIF/srcset.
- **Что сделать:** дать `EditableImage` проп `priority`/`lcp`; в публичной ветке для героя выводить `next/image` с `priority`+`sizes` (или минимум `fetchpriority="high" decoding="async"` без lazy на первом фото). `imgA/imgB` могут остаться `loading="lazy"`. Идеал — весь публичный `EditableImage` перевести на `next/image` (`fill`+`sizes`), сохранив трансформ через `style` на обёртке.
- **Эффект:** заметно раньше стартует LCP главной + автогенерация AVIF/resize. **Трудозатраты:** M. **Уверенность:** high.
- *Связано с B4:* перевод `EditableImage` на `next/image` автоматически лечит и вес крупных product-webp.

### B3. Горячие страницы рендерятся динамически — нет статики/ISR, Cloudflare не кэширует HTML
- **Где:** `src/i18n/server.ts:10` (`getLocale()` читает `headers()`); `app/(main)/layout.tsx:16` (`getIsSuperAdmin()` читает `cookies()`)
- **Проблема:** оба API переводят весь маршрут в dynamic rendering. Ни одна страница (главная, `/catalog`, `/catalog/[category]`, `/product/[slug]`) не имеет статического HTML/ISR — каждый заход посетителя И краулера заново прогоняет полный RSC-рендер (на главной ~50 `EditableText`+`t()`; на каталоге — все товары). `unstable_cache` спасает egress Supabase, но CPU/TTFB на каждый запрос остаётся. При Cloudflare спереди HTML не кэшируется (нет Cache-Control) → краулеры бьют в Render на каждый URL × 3 локали.
- **Что сделать:** вынести чтение locale в generateStaticParams-модель (сегмент `[locale]` в роутинге), чтобы страницы стали статическими с ISR. Минимум — `export const revalidate = 600` на публичных page.tsx + `Cache-Control` (`s-maxage`/`stale-while-revalidate`) через `next.config` `headers()`, чтобы Cloudflare отдавал HTML из кэша. `getIsSuperAdmin` в layout — проверять только при наличии admin-cookie, чтобы не делать layout динамическим для анонимов.
- **Эффект:** самый крупный выигрыш по TTFB/нагрузке на Render + разгрузка от краулеров. **Трудозатраты:** L. **Уверенность:** medium.
- *Дедуплицировано:* находка про дублирующийся `fetchProducts` на главной (`page.tsx:35`, полный каталог ради срезов + весь массив в RSC-пейлоад) — это **следствие** динамического рендера, отдельно чинить не надо; исчезнет после ISR. Дополнительно можно урезать поля, передаваемые в клиентские `HomeCatalogTabs`/`HomePopularPosters`.
