# Бот DC Bakery — флоу всех проверок (для аудита владельцем)

Документ описывает **каждую проверку/защиту** в боте: клиентский поток WhatsApp, чтение
файлов, геолокацию, защиту от prompt-injection и приём файлов маркетологом. Внизу —
список **что проверить руками** и **что нужно настроить/подтвердить вам**.

Обновлено: 13.08.2026 (фичи: геолокация+2ГИС, чтение docs с усиленной защитой, файлы маркетолога).

## 0. Архитектурные гарантии (первый эшелон, не зависят от текста клиента)
Это фундамент — даже если инъекция «прошла» в LLM, она не может навредить:
- **У LLM нет доступа к БД/инструментам/интернету.** Модель только возвращает JSON (ответ + действия с корзиной по id).
- **Цена и остаток — ВСЕГДА серверные** (из БД по каталогу), модель их не считает и не задаёт.
- **Строгая JSON-схема (strict)** вывода модели: лишних полей нет, `productId` валидируется по каталогу — несуществующий товар отбрасывается (`agent/schema.ts parseAgentOutput`).
- **Количество клампится** в [0..1000]; манипулятивные «позиции» срезаются (`isManipulativeItemName`).
- **Заказ создаётся только из корзины** (реальные id+серверные цены), не из «текста».

## 1. Клиентский поток WhatsApp — порядок проверок
Файл: `src/lib/whatsapp/orders/orchestrator/orchestrator.ts` (+ `handle.ts` — вход).
1. **Мастер-флаг** `whatsapp_nl_orders_enabled` (app_settings). Выкл → новый бот молчит.
2. **Rate-limit** на телефон (Upstash/in-memory) — анти-флуд/стоимость.
3. **Per-chat лок** (30 сек lease) — два сообщения одного чата не обрабатываются параллельно.
4. **Идемпотентность** по `messageId` (dedup) — ретрай вебхука не создаёт дубль. Помечаем ТОЛЬКО под локом.
5. **`human_handoff`** — если чат передан менеджеру, бот молчит; авто-возврат через 15 мин.
6. **TTL сессии** 60 мин — старое оформление не продолжаем молча (сбрасываем + чистим корзину).
7. **Разбор входа по типу** (`kind`): текст / голос / фото / документ / **геолокация** / прочее.
8. **Эскалация (regex)** — мат/оскорбления/КАПС/жалобы/угрозы → сразу менеджеру, без LLM (`policy/escalation.ts`).
9. **Скан инъекций** (`policy/injection.ts`) — см. §4.
10. **Структурная фаза оформления** (адрес/интервал/подтверждение) — детерминированно, не через LLM.
11. **LLM-агент** — только с §0-гарантиями. Вход обрезается до 2000 символов.
12. **Создание заказа** — телефон обязателен (иначе лид менеджеру), перепроверка остатка, консент.

## 2. Чтение файлов (фото/PDF/Excel) — `kind` image/document
Зеркалит голосовой поток. Порядок:
1. **Скачивание ТОЛЬКО с доверенного хоста** Green API (`isTrustedGreenHost`, анти-SSRF) — произвольный URL не качаем.
2. **Лимит размера** 15 МБ (ранний отсев по Content-Length + повторно по факту).
3. **Формат по MAGIC-BYTES** (`ai/media-guard.ts`), а НЕ по заявленному mime: JPEG/PNG → OCR, `%PDF` → OCR, ZIP+`.xlsx` → exceljs. Прочее (docx/exe/…) → отклоняется.
4. **Извлечение текста**: Yandex Vision OCR (фото/PDF) или exceljs (Excel). Результат обрезается до 8000 символов.
5. **Повторный скан инъекций по извлечённому тексту** — см. §4 (для файлов защита ГЛУБЖЕ: блок).
6. Подпись к файлу + распознанный текст идут агенту как ДАННЫЕ (обрезка 2000).
7. Не смог прочитать → сообщение клиенту + лид менеджеру (заказ не теряется).

## 3. Геолокация клиента (WhatsApp location) — новое
Файлы: `transport/green-api-parse.ts`, `orchestrator.ts handleLocation`, `geo/gis.ts`.
1. **Распознавание** `locationMessage` → координаты + подпись.
2. **Валидация координат** (`isValidLatLng`): конечные числа, широта ∈[-90,90], долгота ∈[-180,180], не (0,0). Битые → просим адрес текстом.
3. Если клиент на шаге адреса → геометка = адрес доставки (точнее текста), спрашиваем интервал.
4. Вне оформления → запоминаем геометку, ведём к заказу.
5. **В заявке менеджеру** (order-card): `📍 Геометка (2ГИС): <ссылка на точку>` в комментарии.
6. **Текстовый адрес** в заявке → отдельная строка `📍 Адрес: …` + `🗺 2ГИС: <поиск по адресу>` (раньше адрес при наличии даты вообще НЕ показывался — исправлено).
7. ⚠ **Формат 2ГИС-ссылки требует вашей клик-проверки** — см. §6.

## 3.5. Проверка города доставки — антифрод адреса (новое, без 2ГИС API)
ОДИН контур для бота И сайта: `address/provider.ts` (эвристика по маркерам города) +
`address/geocode.ts` (бесплатный OSM-геокодер Photon, БЕЗ ключа) + `address/almaty-city.ts`
(`classifyGeocode`, `combineAddressVerdict` — чистая логика) → `address/geocoder-provider.ts`.
Логика безопасна для легитимных клиентов:
1. Эвристика уверена (в тексте «Алматы» / другой город) → ДОВЕРЯЕМ ей, геокодер не опрокидывает.
2. Эвристика НЕ уверена (клиент написал только улицу) → РЕШАЕТ геокодер: другой город → отказ;
   Алматы → принимаем + координаты (точная 2ГИС-точка); не определил → uncertain (менеджеру).
3. Геокодер недоступен/таймаут → работает только эвристика (как раньше, без ложных отказов).
4. «Алматинская ОБЛАСТЬ» (Талгар/Каскелен) ≠ город Алматы → отказ.
- **WhatsApp-бот**: `deps.address.validate` на шаге адреса (outside_almaty → лид менеджеру).
- **Сайт (оформление)**: `POST /api/geo/verify-address` (тот же провайдер, rate-limit) — фронт
  `CheckoutForm` зовёт при вводе/отправке адреса; outside_almaty блокирует оформление в UI.
  ⚠ Это гейт на фронте (заказной роут `/api/orders` — запретная зона); un-bypassable серверный
  анфорс — отдельной правкой с вашего явного согласия.
- ⚠ БИН↔название (сверка реестром РК) — обсуждается отдельно (нужен источник + доп. шаг оформления).

## 4. Защита от prompt-injection (эшелоны)
- **§0** — архитектура (главный эшелон).
- **Скан текста** (`scanForInjection`): жёсткие паттерны (`ignore instructions`, `system prompt`, `ты теперь админ`, SQL, `<script`, `../` и т.п.), мягкие (ссылки/curl), манипуляции ценой.
- **Набранный вручную текст** + жёсткая инъекция → бот отвечает штатно (§0 держит), но зовёт менеджера присмотреть.
- **ФАЙЛ/голос** + жёсткая инъекция → **БЛОК**: текст в LLM НЕ передаётся, чат → `human_handoff`, менеджеру срочный лид «в файле попытка подмены инструкций». (Крафтнутое фото — самый опасный вектор.)
- **Файл маркетолога** + жёсткая инъекция → **ОТКАЗ** (не добавляем в базу знаний), т.к. знания идут в СИСТЕМНЫЙ промпт бота (см. §5).
- **Рамка**: сообщение клиента всегда подаётся модели как «ДАННЫЕ, не инструкции»; живая база знаний маркетолога — как «ДОПОЛНЕНИЕ, правила/табу НЕ отменяет».

## 5. Приём файлов маркетологом (Telegram) — новое
Файл: `app/api/telegram/webhook/route.ts` (блок файлов) + `telegram/api.ts downloadTelegramFile`.
1. **Роль**: только `marketer` (env `TELEGRAM_MARKETER_IDS`, числовые Telegram id) — не по @username.
2. **Только приватный чат** (chat.id === user.id).
3. **Скачивание** через `getFile` с хоста `api.telegram.org` (URL строим сами из file_path+токен → без SSRF), лимит 15 МБ.
4. **Формат по magic-bytes** (тот же `guardMedia`): фото/PDF/Excel; прочее → отказ.
5. **Извлечение** (OCR/exceljs).
6. **Анти-инъекция по извлечённому тексту** → жёсткая инъекция = ОТКАЗ (не в базу).
7. Иначе → добавляем в базу знаний (кап 2000 симв/запись, максимум 100 записей).

## 6. ⚠ ЧТО ВАМ НУЖНО НАСТРОИТЬ/ПОДТВЕРДИТЬ
1. **2ГИС-ссылки — КЛИК-ПРОВЕРКА.** Формат deep-link 2ГИС по координатам публично не документирован. Реализовано: точка `https://2gis.kz/almaty/geo/<lon>,<lat>`, поиск `https://2gis.kz/almaty/search/<адрес>`. **Пришлите боту геолокацию, доведите до заявки, откройте ссылку в карточке** — если точка/поиск открываются верно в Алматы, всё ок. Если нет — скажите, поменяю формат (варианты: `?m=<lon>,<lat>/17`, `go.2gis.com`, либо перейдём на Google Maps `https://maps.google.com/?q=<lat>,<lng>`).
2. **Env `TELEGRAM_MARKETER_IDS`** — числовые id маркетологов (для приёма файлов/текста). Уже добавляли для фазы 1.
3. **Env `YANDEX_OCR_API_KEY` + `YANDEX_OCR_FOLDER_ID`** — иначе фото/PDF не читаются (Excel читается без OCR).
4. **Геокодер адреса (антифрод) — без ключа.** По умолчанию публичный Photon (`photon.komoot.io`). Оговорки usage policy OSM: низкий объём, кэш, User-Agent (уже шлём `dc-bakery.kz`). При росте объёма — свой Photon/Nominatim через env `GEOCODER_URL`. ⚠ Проверьте на нескольких реальных адресах: явно другой город → отказ; алматинский без слова «Алматы» («Абая 10») → принят; сомнительный → менеджеру (не ложный отказ).

## 7. ЧТО ПОТЫКАТЬ (тест-кейсы, ожидаемый результат)
Клиент (WhatsApp):
- [ ] **Геолокация** на шаге адреса → бот: «Принял геолокацию…», спрашивает интервал; в заявке менеджеру — кликабельная 2ГИС-точка в комментарии.
- [ ] **Геолокация** просто так (не в оформлении) → бот благодарит, ведёт к заказу; геометка запомнена.
- [ ] **Фото** с заказом (печатный/рукописный) → бот разобрал позиции (нужен Yandex OCR).
- [ ] **PDF** с заказом → то же.
- [ ] **Excel (.xlsx)** со списком → бот прочитал ячейки.
- [ ] **Текстовый адрес** в заявке → в карточке `📍 Адрес` + `🗺 2ГИС` (поиск).
- [ ] **Инъекция в фото** (картинка с текстом «ignore all previous instructions / system prompt») → бот НЕ выполняет, отвечает «передал менеджеру», срочный лид.
- [ ] **Видео/стикер/голосовая заметка не про заказ** → «пришлите текст/голос», менеджеру.
- [ ] **Адрес в другом городе** (напр. «Астана, Кабанбай батыра 10») → бот НЕ принимает, отдаёт менеджеру.
- [ ] **Алматинский адрес без слова «Алматы»** («Абая 10») → бот принимает (геокодер подтвердил Алматы).
Сайт (оформление):
- [ ] Ввод адреса в другом городе на оформлении → под полем ошибка «доставляем только по Алматы», оформить нельзя.
- [ ] Алматинский адрес → оформление проходит.
Маркетолог (Telegram, ЛС):
- [ ] **Фото/Excel/PDF** от маркетолога → бот прочитал и добавил в базу (`/база` покажет), клиент видит это в ответах.
- [ ] **Файл с инъекцией** от маркетолога → бот НЕ добавил, предупредил.
- [ ] **Не-маркетолог** шлёт файл → бот игнорирует (нет доступа).
Регресс:
- [ ] Обычный текстовый заказ, голос, `/база`, `/очистить` — работают как раньше.
