# Доступ для торговых представителей (роль `manager`) — план

Вводные владельца (10.08): торгпред видит **всех** клиентов + все остатки/цены; заказ атрибутируется к торгпреду; клиента заводит **с нуля, без OTP**.

## Как сейчас (факт по коду)
- Вход в админку — Supabase-auth через `proxy.ts` (`adminProxy`, cookie `ADMIN_ACCESS_COOKIE`). Личность: `src/lib/admin-access.ts` `isAdminIdentity` = `app_metadata.role==="admin"` ИЛИ email в `ADMIN_EMAILS`.
- **Проверка доступа — в proxy, не в роутах** (из ~15 `/api/admin/*` только settings/login/logout проверяют сами). → гейт по роли ставим в proxy = один чокпоинт.
- «Обычный админ» = ПОЛНЫЙ доступ (заказы, товары/цены, оплаты, настройки). Разница «суперадмин» (`SUPERADMIN_EMAILS`) — только правка сайта.
- Создание клиента в админке НЕТ (страница `/admin/clients` — только просмотр). Клиент создаётся самообслуживанием + OTP.

---

## СТАДИЯ 1 — рабочий доступ торгпреду (≈1 час, безопасно, без FORBIDDEN-зон)
Цель: торгпред логинится в `/admin`, **видит всё** (клиенты/заказы/товары/остатки/цены), но опасные действия заблокированы.

1. **Роль `manager`.** `src/lib/admin-access.ts`:
   - Новый `getAdminRole(user): "admin" | "manager" | null`. `manager` = `app_metadata.role==="manager"` ИЛИ email в новом `MANAGER_EMAILS` (быстрый способ назначить без дашборда — как `ADMIN_EMAILS`).
   - `isAdminIdentity` начинает возвращать true и для `manager` (чтобы proxy пускал в /admin). Суперадмином manager НЕ становится (в `SUPERADMIN_EMAILS` его нет → правку сайта не получает ✓, уже так).
2. **Default-deny опасных операций для manager — в `proxy.ts`** (⚠️ FORBIDDEN-зона, нужно «ок» владельца; но это ЕСТЬ место авторизации админки):
   - После подтверждения личности: если роль `manager` и запрос **мутирующий** (`POST/PATCH/PUT/DELETE`) к `/api/admin/*`, а путь НЕ в белом списке разрешённого торгпреду → `403`.
   - Также заблокировать manager-у страницы: `/admin/settings`, `/admin/products*` (цены), — редиректом/403.
   - Белый список для manager (стадия 1 пустой; расширяется в стадии 2–3).
3. **UI-скрытие** (не защита, а удобство): в admin-компонентах прятать кнопки оплат/цен/настроек, если роль `manager` (прокинуть роль в layout).
4. **Назначение:** создать торгпреду Supabase-пользователя, `app_metadata:{role:"manager"}` (или добавить его email в `MANAGER_EMAILS` на Render — быстрее). Логин на `/admin/login`.

Итог стадии 1: торгпред работает с тем, что уже есть (просмотр всего), без риска сломать оплаты/цены.

## СТАДИЯ 2 — завести клиента с нуля без OTP (net-new, аккуратно, ~час+)
5. **`POST /api/admin/clients`** (manager+admin): валидация (компания, БИН, телефон, адрес), вставка в клиентскую таблицу через `service_role`, **без OTP**, `phoneVerified` по решению. Идемпотентность по телефону.
6. **Форма** «Новый клиент» на `/admin/clients` (кнопка видна admin/manager).
7. Добавить путь из п.5 в белый список proxy для manager.
⚠️ Клиентские таблицы (`clients`/`whatsapp_clients`) — только `service_role` + был инцидент RLS. Аккуратно.

---

## СТАДИЯ 3 — заказ от имени клиента + атрибуция (FORBIDDEN + миграция, только с ревью, НЕ за час)
8. **Проведение заказа менеджером** — переиспользует `insertOrderWithItems`/`app/api/orders/route.ts` = **FORBIDDEN** (заказы/оплаты). Только с ревью.
9. **Атрибуция** — поле `created_by`/`manager_id` в заказе = **миграция БД** (твоё добро). Плюс отчёт «заказы по торгпреду».

**Пока Стадии 3 нет** — торгпред уже может провести заказ обычным клиентским путём (каталог→корзина→чекаут от лица клиента); стадии 2–3 лишь удобство + атрибуция.

---

## Что можно сделать в «ближайший час» безопасно
Только **Стадия 1** (+ возможно начать Стадию 2). Стадии 2–3 трогают FORBIDDEN-зоны и миграцию — рассчитывать на них в часе нельзя.
Нужно «ок» на правку **`proxy.ts`** (гейт роли). Ветка — отдельная от `b3-locale-isr` (эта фича идёт от `main`).
