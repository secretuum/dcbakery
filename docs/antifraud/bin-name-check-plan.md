# Антифрод: сверка БИН ↔ официальное название компании

**Статус:** дизайн-предложение (код НЕ написан). Ждёт добро владельца на реализацию.
**Дата:** 13.08.2026. Автор ресёрча/дизайна: сессия Claude.
**Связано:** PR #9 (антифрод адреса «в Алматы» на OSM/Photon) — тот же паттерн «мягкий сигнал менеджеру + чистый тестируемый модуль».

---

## 1. Цель

По БИН клиента получить **официальное название юрлица из госреестра** и сверить с тем,
что клиент указал сам (поле «название компании»), чтобы поймать несоответствие
(«наврал про компанию») и подсунуть менеджеру красные флаги (лжепредприятие, банкрот,
недействующий БИН, налоговые долги).

## 2. Решения владельца (зафиксированы 13.08.2026)

| # | Развилка | Решение |
|---|----------|---------|
| A | Жёсткость реакции | **Мягкий сигнал менеджеру.** Проверяем в фоне, вердикт прикрепляем к заказу/лиду, менеджер решает. НЕ блокируем заказ (ложные срабатывания + падение API не должны терять клиентов). |
| B | Объём проверки | **Название + фрод-профиль** (статус, город, чёрные списки). |
| C | Тип клиента | Не все клиенты — юрлица. **Кнопка-селектор «Юрлицо / ИП / Физлицо»** при регистрации или первом заказе. Сверка по БИН — только для Юрлица и ИП; Физлицо БИН не имеет → проверку пропускаем. |

## 3. Источник данных (результат ресёрча)

Проверены вживую бесплатные источники по БИН (тест-БИН Kaspi `971240001315`, ТОО `021240009908`, фейк `000000000000`):

| Источник | Ключ/авторизация | Название по БИН | Вердикт |
|---|---|---|---|
| **`apiba.prgapp.kz/CompanyFullInfo?id=<БИН>&lang=ru`** (бэкенд ba.prg.kz / БизнесАналитика) | **не нужен** | ✅ RU+KZ, статус, директор, адрес+город, ОКЭД, НДС, чёрные списки | ✅ **основной** |
| `data.egov.kz` gbd_ul (офиц. открытые данные) | **нужен ключ** (беспл. регистрация) | ✅ авторитетно | 🟡 запасной/легитимный |
| `stat.gov.kz` counter API | — | ✖ теперь **404** | ✖ умер |
| `pk.uchet.kz` / `adata.kz` | — | ✖ (мои пробы эндпоинтов = 404) | ✖ не приоритет |

### 3.1. Основной эндпоинт `apiba.prgapp.kz/CompanyFullInfo`

- **Метод:** `GET https://apiba.prgapp.kz/CompanyFullInfo?id=<БИН>&lang=ru` (есть и `lang=kz`).
- **Ключ/авторизация:** не требуется. CORS открыт. Сервер Kestrel (ASP.NET Core).
- **Рейт-лимит (из заголовков ответа):** `X-Rate-Limit-Limit: 7d`, `X-Rate-Limit-Remaining` стартует с **20000** → **~20 000 запросов / 7 дней на IP** (~2800/день). Для нашего потока (единицы новых клиентов в день) — запас колоссальный. Считается по IP сервера Render (все наши запросы с одного IP — норм).
- **Латентность:** ~0.1–0.5 c.

Нужные поля ответа (проверены):

```
basicInfo.titleRu.value      → "АО \"KASPI BANK\""            (официальное название, рус)
basicInfo.titleKz.value      → "\"KASPI BANK\" АҚ"           (каз)
basicInfo.bin                → "971240001315"
basicInfo.status.value/.description → 0 / "Активен"
basicInfo.ceo.value.title    → "МИРОНОВ ПАВЕЛ ВЛАДИМИРОВИЧ"   (директор)
basicInfo.addressRu.value    → полный юр. адрес
basicInfo.cityName           → "Г.АЛМАТЫ"                     (усиливает Алматы-гейт!)
basicInfo.crumbsKato.nameRu  → "Алматы"
basicInfo.primaryOKED.value  → вид деятельности (ОКЭД)
basicInfo.isNds.value        → true/false (плательщик НДС)
basicInfo.isDeleted          → true у несуществующих/удалённых
basicInfo.isIndividual       → true у ИП/физлиц
```

**Фрод-профиль (тот же бесплатный ответ):**

```
debtsInfo.kgd.totalDebt / totalFine     → налоговая задолженность (КГД)
reestrs[] — массив реестров КГД/госзакупок, у каждого:
  .description  (что за список)
  .isIntruder   (true = клиент в этом чёрном списке)
  .violation    (код): 4=лжепредприятие, 3=банкрот, 0=бездействующий,
                 1=отсутствует по юр.адресу, 5=регистрация недействительна,
                 2=налоговая задолженность, 7=перерег. недействительна,
                 8=ограничена выписка ЭСФ; отдельно — недобросовестный участник госзакупок
```

Красный флаг = `reestrs.some(r => r.isIntruder)` (особенно лжепредприятие/банкрот/недействующий) **или** `status ≠ Активен` **или** `debtsInfo.kgd.totalDebt > 0`.

### 3.2. Поведение на крайних случаях (проверено)

- **Несуществующий/битый БИН** (`000000000000`) → HTTP **200**, но `titleRu.value = null`, `isDeleted = true`. «Не найдено» ловится по `!titleRu.value`.
- **Короткий/невалидный id** (`123`) → HTTP **404**.
- **Обычное ТОО** (не только крупняк) → отдаётся корректно (проверено на «ТОО KASPI OFFICE», Алматы).

### 3.3. Риски источника (влияют на дизайн)

1. **Недокументированный приватный бэкенд** ba.prg.kz, не официальное публичное API → может измениться/лечь/сменить формат без предупреждения. **Вывод:** обращаться best-effort, изолировать за интерфейсом провайдера, при любой ошибке/таймауте — **тихо пропускать** (нет вердикта ≠ отказ клиенту). Это ровно причина, почему владелец выбрал «мягкий сигнал», а не жёсткий блок.
2. **Нечёткость названия:** клиент пишет «Ромашка», реестр — `ТОО "РОМАШКА"`. Нужна нормализованная/фуззи-сверка, не точное равенство (см. §5).
3. **Запасной легитимный путь:** если prgapp станет ненадёжен — `data.egov.kz` gbd_ul (нужен бесплатный apiKey, регистрация). Заложить в интерфейс провайдера как альтернативную реализацию, переключаемую env.

## 4. Модель данных: тип клиента

Добавить `customer_type: 'legal' | 'ip' | 'individual'` (Юрлицо / ИП / Физлицо).

| Тип | Обязательные поля идентификации | БИН-сверка |
|-----|--------------------------------|------------|
| **legal** (ТОО/АО) | `company_name` + `customer_bin` (12 цифр) | ✅ сверяем название + фрод-профиль |
| **ip** (ИП) | ФИО/название + `customer_bin` (= ИИН, 12 цифр) | ✅ сверяем (название ИП фуззи-мягче, часто «ИП ФИО») |
| **individual** (физлицо) | ФИО + телефон | ✖ БИН нет — проверку пропускаем |

**Где селектор (по решению владельца):** сегментированная кнопка «Юрлицо / ИП / Физлицо»
при регистрации ИЛИ при оформлении первого заказа. От выбора зависят обязательные поля
формы и запускается ли БИН-сверка.

**Сегодня в коде:** `Order.company_name` обязателен, `Order.customer_bin` — опционален,
типа клиента нет. `customer_bin` в `CheckoutForm` собирается, но не валидируется.

**⚠ Открытый вопрос для владельца (см. §7):** «Физлицо» на строго-B2B сайте — это
самозанятый/незарегистрированный B2B-клиент, а не розница? В `CLAUDE.md` действует правило
«strictly B2B, NO B2C». Нужно явно подтвердить трактовку и текст оферты для физлица.

## 5. Логика проверки (чистые тестируемые модули)

Паттерн — как `src/lib/address/almaty-city.ts` из PR #9: сеть изолирована, ядро чистое и покрыто тестами.

Предлагаемая структура `src/lib/antifraud/`:

- **`bin-format.ts`** (чисто) — валидация БИН/ИИН: строго 12 цифр, только цифры. (Опц. классификация юрлицо/ИП по структуре БИН — не переусложнять.)
- **`name-match.ts`** (чисто, с тестами) — `normalize(name)`: в нижний регистр, срезать орг-форму (ТОО/АО/ИП/ЖШС/АҚ/ООО/…), кавычки «»"'`, лишние пробелы, латиница↔распространённые дубли. `compareNames(entered, official)` → `{ verdict: 'match' | 'fuzzy' | 'mismatch', score }`. Порог фуззи — по подстроке/расстоянию Левенштейна.
- **`company-registry.ts`** — интерфейс `CompanyRegistryProvider { lookup(bin): Promise<CompanyRecord | null> }` + реализация `PrgAppProvider` (fetch prgapp, парс в узкий `CompanyRecord`). Env: `COMPANY_REGISTRY_URL` (дефолт `https://apiba.prgapp.kz`), таймаут ~4 c, при ошибке → `null` (не бросать). Узкий тип:
  ```ts
  type CompanyRecord = {
    found: boolean;
    titleRu: string | null; titleKz: string | null;
    status: string | null;        // "Активен" / …
    cityName: string | null; addressRu: string | null;
    ceo: string | null; primaryOked: string | null;
    flags: { fakeCompany: boolean; bankrupt: boolean; inactive: boolean;
             taxDebt: boolean; badGoszakup: boolean };
    debtTotal: number;
  };
  ```
- **`verdict.ts`** (чисто, с тестами) — `buildBinVerdict(entered, record)` → структурный вердикт для менеджера: `{ nameMatch, redFlags: string[], notFound, cityOutsideAlmaty }` + человекочитаемая строка.

**Никогда не блокируем на этом (решение A).** Нет записи / ошибка API / фуззи-несовпадение — только пометка менеджеру.

## 6. Куда встраивается (архитектура)

Цель — **обойти FORBIDDEN-зону** (`app/api/orders/**`, `src/lib/supabase/admin.ts`): антифрод по решению A — сигнал менеджеру, а не гейт, поэтому его можно навесить на **этап уведомления менеджера**, не трогая создание заказа.

1. **Уведомление в Telegram** (`src/lib/telegram/order-card.ts`) — при сборке карточки заказа, если у заказа есть `customer_bin`, дёрнуть registry и дописать блок: `Реестр по БИН: официально «ТОО …», статус Активен, г. Алматы. ⚠ Клиент указал «…» — не совпадает.` / `🔴 В списке лжепредприятий`. Telegram-модуль — не FORBIDDEN.
2. **Карточка заказа в админке** (`app/(unlocalized)/admin/orders/[id]/page.tsx`) — тот же вердикт в UI для менеджера (через новый серверный роут `GET /api/antifraud/verify-bin?bin=…`, rate-limit как у `/api/geo/verify-address`).
3. **Checkout (опц., как в PR #9)** — `onBlur` поля БИН зовёт `/api/antifraud/verify-bin`, показывает клиенту мягко («проверим при подтверждении»); жёсткого гейта нет.
4. **Бот (позже, отдельная задача)** — добавить сбор БИН + тип клиента в поток, тот же registry-модуль, вердикт — в эскалацию/лид менеджеру (`policy/escalation-context.ts`). Сейчас бот БИН не собирает.

**Опц. серверное enforcement** (если владелец позже захочет жёсткий гейт для юрлиц): проверка в `validateOrderFields`/роуте `/api/orders` — это **FORBIDDEN-зона**, требует явного ОК владельца. По умолчанию НЕ делаем (решение A = мягко).

## 7. Ответы владельца (получены 13.08.2026 — можно писать код)

1. **БИН обязателен** для Юрлица (legal) и ИП (ip); для Физлица (individual) — не требуем.
2. **«Физлицо» = самозанятый / незарегистрированный B2B-клиент** (НЕ розница). Уживается с B2B. ⚠ **Действие владельца:** прописать отдельную **оферту/условия для физлица** (юр-текст — владелец/юрист; это не код).
3. **Клиенту показываем** мягкую пометку при вводе БИН — «БИН на проверке». Жёсткого гейта нет. Полный вердикт (совпадение/фрод-флаги) — менеджеру.
4. Порог фуззи-сверки названия — подберём на реальных данных после связки 1.

## 8. Оценка объёма (когда дадут добро)

Ориентировочно 3 связки, каждую — отдельным заходом/веткой (правило «макс 3 файла на патч»):

- **Связка 1 (ядро, без UI):** `antifraud/bin-format.ts` + `name-match.ts` + `verdict.ts` (+ тесты). Чисто, безопасно, никакие FORBIDDEN не трогает.
- **Связка 2 (провайдер + роут + Telegram):** `antifraud/company-registry.ts`, `app/api/antifraud/verify-bin/route.ts`, обогащение `telegram/order-card.ts`.
- **Связка 3 (UI типа клиента):** селектор «Юрлицо/ИП/Физлицо» + условная валидация полей в регистрации/checkout; вердикт в админ-карточке заказа.

Бот (сбор БИН + вердикт в эскалацию) — отдельной, четвёртой задачей.
